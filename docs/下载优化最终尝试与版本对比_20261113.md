# 下载优化最后一轮尝试与版本选择

后续状态：用户随后选择恢复 batch，并要求明确的自定义时间入口，已完成。当前运行版本和验证见[开发契约](开发契约.md)的“2026-11-13 恢复 batch 并增加自定义时间预算”。本文以下保留切换前的实验记录；其中实验脚本应在 `../checkpoints/download-experiments-before-stable-20261113/source` 配套源码中运行。

本轮没有达到“保住 5 篇，同时稳定缩短整个任务等待”的推广门槛。断点续传在受控中断后的真实下载中有效，但尚不能解决已观察到的主要耗时来源。因此本轮仅新增诊断脚本、测量记录和本文；没有修改应用源码、默认配置或正在运行的服务。旧版快照继续保留，是否启用滚动替补交由用户决定。

## 本轮尝试：带版本校验的断点续传

目标是避免慢下载被中止后从头传输。先验证实际来源支持 HTTP Range，再比较重下与续传；不引入更多并发、不放宽 PDF 完整性或版本校验，不调用付费模型。

- 对上一轮下载过的 3 篇公开 arXiv PDF，各请求首段和中间段，共 6 次真实请求。全部返回 206，Content-Range 正确，内容与本地已验证 PDF 的对应 64 KiB 切片逐字节一致。
- 其中 MemReader v2 返回合法强 ETag，第二段附带 If-Range 后仍一致。另外两个响应的 ETag 未带引号，本次未把它们当作强校验器，也未验证 Last-Modified 续传条件。不能将 6 次分段成功扩大为所有来源都可安全拼接。
- 按预先写入协议的 AB / BA 顺序，对 MemReader v2 做 2 组恢复对照。每组先刻意中断一次正常下载，保留共享前缀，再分别完整重下和条件续传。读取块可能跨过 512 KiB，因此按实际保留字节发 Range。
- 4 份完整恢复结果均与原 PDF 的 SHA256 一致。这里只测真实网络上的人工中断恢复，不是自然失败率实验，也没有重跑完整五篇研究流程。

| 配对 | 已收到的共享前缀 | 从头重下的恢复耗时 | 条件续传的恢复耗时 | 少传字节 | 含共享前缀的总流量降低 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1：重下→续传 | 538,009 | 2.782 秒 | 1.796 秒 | 538,009 | 28.4% |
| 2：续传→重下 | 524,288 | 5.656 秒 | 3.625 秒 | 524,288 | 27.9% |

含首次前缀下载的耗时分别为 6.688→5.702 秒、9.844→7.813 秒。不能把恢复段约 36% 的降幅当作整个系统提速。本次网络明显较快，两组、单篇样本不足以证明长期延迟改善；上游 CDN 缓存不可控。

协议依据：[RFC 9110 Range](https://www.rfc-editor.org/rfc/rfc9110.html#section-14.2)、[If-Range](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.5)。服务器可以忽略 Range；未验证的响应不能直接拼接进旧前缀。

## 为什么这还不够支持更新

本轮重新读取上轮六个 run，逐篇逐 pass 统计；存在 `fulltext_passes` 时不再重复计入末次 `downloads`。

| 六轮中记录的事件 | 次数 | 对续传的含义 |
| --- | ---: | --- |
| 候选地址时间预算到期 | 6 | 需跨候选/阶段保存前缀，并在下一次获准尝试中恢复 |
| 单篇总预算到期 | 4 | 不能在当前调用中擅自延长预算 |
| 快速阶段预算到期 | 9 | 其中 3 次尚在排队，没有正文可续传 |
| 全文总预算 600 秒到期 | 0 | 本轮未发生 |
| httpx 连接/读取异常 | 0 | 仅给网络异常重试增加续传，直接覆盖此次已观察异常为 0 |
| 没有开放 PDF 地址 | 6 | 同一原始入选论文每轮一次，续传无法解决 |

三轮 batch 的 15 个请求均完成。三轮 progressive 有 15 个完成、16 个已发起后被预算取消、3 个排队取消。16 个传输中止累计收到 6,482,363 字节；其中有最终不需要的备用论文，不能直接把全部字节当作可节省流量。

现有 `_fetch` 中正文是局部缓冲；候选、单篇和阶段取消都会退出。只修改 `except httpx.RequestError` 不会覆盖上述预算取消。真正覆盖它们需要跨阶段前缀状态、验证器及清理策略，且仍须遵守原硬预算、用户取消和补足后停止规则。这超出了本轮已证明有效的改动范围。

因此本次保留独立验证，不接入生产下载器，也不恢复已否决的短超时方案。慢但持续成功的连接，是 batch 当前长尾的重要来源；仅减少中断后的重传不足以证明它能改善这种长尾。

## 当前优化版与旧版的具体区别

此处“旧版”指 `../checkpoints/download-before-20261112-streaming/source`，即时间预算界面及排队计时修复之后、滚动替补之前的源码。另一个 `download-before-20261112-stability/source` 快照已包含 batch/rolling，用于保留短超时试验前版本。

| 项目 | 旧版 batch | 当前可选 rolling |
| --- | --- | --- |
| 原 Top-k | 先处理原入选论文 | 相同，仍等待原 Top-k 完成 |
| 失败替补 | 按排名分批；缺一篇时可能逐篇等待 | 在既有并发上限内启动后续候补，先完成可读正文者补位 |
| 重复下载地址 | 不做新增的同版地址归并 | 合并实际指向同一 arXiv 版本的地址；不同版本和镜像保留 |
| 补满后的任务 | 等待当前批次结束 | 取消多余下载，已启动转换正常收尾；保留取消/未采用审计 |
| 时间预算 | 默认 45/180/180 秒；慢网 90/240/600 秒 | 相同；预算面板不是 rolling 独占功能 |
| 实际替补论文 | 偏向候补排名顺序 | 受完成顺序影响，最终论文集合可能变化 |
| 适用场景 | 保留原有选取和等待行为 | 减少坏候补阻挡后续可用候补的等待 |

候选、单篇、全文阶段分别对应上述三项预算。rolling 在关闭对话框“并行优化”时宽度为 1，不会获得并发替补收益。已记录真实对照全部固定并发 3。

当前版另增排队、响应头、首字节、接收字节和取消等诊断。这有助于解释等待，但本身不是提速。来源、排序、版面解析和单篇分析算法与上述下载快照一致，不能把这些既有功能再次算作本轮新增收益。

## 已有可比较的实际效果

以下为本轮重新读取原始产物后的历史结果，未重新执行模型调用。固定长期记忆候选、慢网预算 90/240/600 秒、并发 3、关闭本地 PDF 缓存，使用 layout + evidence_fast；不含搜索、Selector 和最终综合报告。

| rolling 配对 | 旧版 batch：正文＋笔记 | rolling：正文＋笔记 | 可用篇数 |
| --- | ---: | ---: | --- |
| 第一组 | 78.11 秒 | 237.75 秒 | 两边均为相同 5 篇正文、5 篇笔记 |
| 第二组，执行顺序反转 | 89.31 秒 | 63.51 秒 | 两边均为相同 5 篇正文、5 篇笔记 |

一慢一快，不能证明线上稳定更快。第一轮 rolling 发生在取消审计与转换收尾修复之前，取消请求统计可能偏低；保留这轮耗时与成功篇数，不因其较慢而剔除。单一主题、两组对照也不能证明答案准确率不变。

progressive 短超时两阶段试验的三组下载＋解析耗时：batch 102.30 / 114.64 / 194.15 秒；progressive 323.46 / 149.91 / 174.95 秒。两边均有 5 篇完整正文，但新方案只赢 1/3，中位数从 114.64 升至 174.95 秒，观察最慢值从 194.15 升至 323.46 秒。因此不推广，前端没有该方案的新选入口，仅保留 CLI 和历史配置复现。

27 次受控模拟中的坏候补阻塞场景支持 rolling 的机制价值，约 79% 的等待减少仅属于该模拟。真实同哈希 PDF 的传输段曾为 9.7 / 9.7 / 36.7 秒，说明网络波动确实存在；不能据此判定是本机运营商还是远端服务。

建议保持 batch 作为日常默认。rolling 可作为针对性机制和课程对照展示，但目前不应以“稳定保住 5 篇且更快”为理由推荐切换。5 篇是本组条件下的观测结果，不是任意网络条件下的保证。
