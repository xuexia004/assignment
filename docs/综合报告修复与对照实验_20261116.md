# 综合报告截断与格式修复对照

已实现并验证综合报告的结构化生成：完整读取原有五份笔记，只生成一份结构化内容，再由已有渲染器形成报告，避免同时生成长正文和重复结构字段。最终修订版在三对同笔记实验中，报告可读及严格通过均为 **3/3**，旧版为 **0/3**；报告墙钟中位数 **9.27 秒对 22.81 秒**，下降约 **59.3%**。旧版这三次均在 4000 输出 token 处截断。

这证明了本组输入下报告可用性的改善，不代表旧版成功交付一份报告需要 22.81 秒，也不是完整检索任务提速或事实准确率结论。新版报告更精简、采用结构化排版；没有声称在相同篇幅下加速。有限人工核验仍发现成本口径及无依据否定判断，见下文。

## 实现及旧版开关

- `report_strategy=legacy` 保留原有自由 Markdown＋结构字段、原提示词、一次生成及原校验行为。
- `report_strategy=structured` 完整提交所有可用笔记，要求概述、相关工作、逐篇/跨篇比较、已研究问题、局限、方向、真实引用七项；比较必须覆盖每篇输入，并有非空机制、证据与条件、局限。由既有渲染器产生 Markdown，不让模型再写一次重复正文。
- 原严格 schema、引用 ID/标题/完整集合检查继续执行；不靠把字符串强转数组、拼接残缺 JSON、删掉引用验证或伪造字段制造成功。
- 明确的长度截断、JSON 解析和结构/引用错误，最多再发一次完整生成请求，包含原始全部笔记和安全字段级反馈；再次失败保留失败。过滤、传输或预算错误不触发这次格式恢复；原客户端的 HTTP 重试仍受原预算约束。
- 客户端继续拒收截断/过滤响应，额外保留 `finish_reason` 供区分原因；`metrics.report_generation` 记录策略、尝试数、失败原因、输入哈希及修复次数。成功修复的中间错误留在审计，不作为最终报告错误；原有部分输入仍为部分报告。
- 模型、输入笔记、输出 4000 token 上限不变；输入超预算显式失败，不截掉笔记。没有新增依赖或修改后端业务模型字段。

依据包括 [DeepSeek JSON Output 官方说明](https://api-docs.deepseek.com/guides/json_mode/)：JSON 模式需要清楚的格式提示及示例，输出容量不足仍会截断。本方案在已有 JSON 模式之上补足字段示例、篇幅约束、本地严格校验和有界恢复；不把 JSON 模式当作 schema 或事实正确性保证。

设置入口：**设置 → 研究方法开关 → 05 综合报告 → 综合报告方法**。可选择“旧版自由生成（基线）”或“结构化生成与格式修复”，点击“保存研究方法”后只用于新任务。“全部恢复基线”同时选择旧报告策略。该开关独立于单篇分析和旧命名预设；选择 `baseline` 预设本身不会覆盖显式报告选择。

通过复验后，`Settings` 与环境缺省值改为 `structured`；已经保存的显式 `legacy` 设置继续优先。命令行可用 `PAPER_AGENT_REPORT_STRATEGY=legacy` 保留旧对照。现有用户配置未写回；正在运行的旧桌面服务需要重启后才能加载新增设置。旧结果和冻结源码原样保留。

## 对照设计

问题仍为“长期记忆如何降低 Agent 的推理成本？”，使用上一轮相同五篇真实论文及提取文本，模型 `deepseek-flash`，关闭 thinking、温度 0、输出上限 4000、同一环境、每个逻辑请求沿用原生客户端生命周期。未增加连接池或修改下载链路来制造报告提速。

1. **首批固定笔记三对**：复用历史 `replay-round-03-old_serial` 的五份完整可用笔记。每对报告的笔记和实际请求中的 `summaries` 哈希相同，交换执行顺序。
2. **首批重新分析三对**：同五篇论文每轮重新做 direct 多篇并行分析，各取得五份笔记后，两种报告策略共享该轮笔记；共 15 次新的单篇模型调用，不复用旧答案。
3. **提示词修订后三对**：人工检查首批输出后，补强数值与数据集/基线/单位/阶段绑定，以及逐篇归属和不确定性表达，再用原五份固定笔记做三对。此修订依据同组开发反馈，属于开发复验，不是独立准确率留出评测。

每个真实请求先落盘预留预算，全任务硬上限为 50 次物理请求、200 万保守单位（请求消息 UTF-8 字节＋输出 token 容量，非计费 token）。两批共享账本，失败也占预算；连续三次基础设施错误停止。实际 **33 次请求、1,972,131 保守单位**，没有扩充上限。HTTP 重试在实验中统一关闭；结构化方案仍允许一次格式恢复。全部慢值及失败保留，没有剔除。

本实验调用原生 pipeline 的单篇分析/报告阶段，检索、下载和 PDF 转换已冻结并跳过，明确不称为端到端实验。生产流程继续通过 MainAgent 和官方 MCP；完整协议与桌面流程另用标记清楚的离线夹具回归。

## 实测结果

报告墙钟单位为秒；每格为中位数和范围，统计全部三次。可读/严格通过在本组一致；严格通过包括五份完整笔记及引用条件，仍不等于事实正确。

| --- | ---: | ---: | ---: | ---: | ---: |
| 首批方案，固定五份笔记 | 0/3 | 3/3 | 23.50 [20.64, 23.99] | 8.73 [7.99, 8.91] | 0 |
| 首批方案，重新分析同五篇 | 0/3 | 3/3 | 23.17 [20.50, 23.27] | 9.11 [8.89, 9.25] | 0 |

首批方案与最终修订版分开，不把九份新报告合并成最终版九轮证明。最终修订版没有重复做三轮新笔记生成，不能把首批的鲜生成结果写成最终版的独立实测。

首批重新分析的五篇阶段墙钟分别为 28.96、29.64、28.74 秒，三轮都取得 5/5 可用笔记，合计 15/15。报告阶段与五篇分析耗时分开记录。

## 内容核查与仍存问题

首批结构通过后没有直接宣称质量合格。人工对照输入笔记发现：DimMem 的两套数据集指标连写时省略条件，Agent Zero 的架构意图被写成实测收益，以及一篇缺少组件消融的限制被错误推广到另一篇。随后只补通用约束，没有把这五篇的名称或正确数字硬编码进提示词。

最终三份报告都明确区分 DimMem 的 LoCoMo 与 LongMemEval-S 指标，原有“共同减少上下文换准确率”和“二者均无组件消融”等表述未原样再现，并区分 token、嵌入次数、GPU 时间、费用与时延。

但人工核验仍有具体反例：第三份把已计入 GPU 时间的交叉编码器开销写成“另计”，并从材料未报告推出两篇都未做有/无记忆对照；第一、二份对 Agent Zero 缺少某些组件消融的概括仍偏宽。输入笔记自身也存在模型数量枚举不一致等问题，综合阶段不能据此保证原论文事实。

因此本次只宣称**截断与格式可用性改善、完整输入及引用约束保留**，不宣称事实准确率不下降。输出更精简可能丢失条件，后续质量评测应继续检查数字口径、否定判断及上游笔记忠实度。新增单篇证据方法的 `citation_quote_mismatch` 属于另一环节，本次未修改。
